Entwicklungsgeschichte

Phase 1 — Ursprung
Monolithischer Solver

Die ursprüngliche Codebasis bestand aus einem einzigen EqnSystem.java mit eingebettetem Parsing, Jacobi-Aufbau und Newton-Iteration. Der Solver verwendete gedämpftes Newton ohne Liniensuche.

  • GUI-gekoppelt: Solver-Code importierte Swing-Klassen (HTMLDocument, JTextPane)
  • Fixe Dämpfung (0.5–1.0) statt adaptiver Liniensuche
  • Alle Variablen per Name-String verfolgt — Aliases nicht getrennt
  • Keine Exception-Hierarchie — Fehler als Flags zurückgegeben
  • Broyden-Variante (NewtonBroydenGMRES) als separate Klasse mit GMRES
Phase 2 — Strukturierung
Strukturelles Refactoring

Systematisches Refactoring trennte Verantwortlichkeiten in eigenständige Klassen:

  • InitGuessApplier aus EqnSystem.run() extrahiert
  • EqnSysReaderGui vom Backend EqnSysReader getrennt
  • SolverLogger als zentralisierte Logging-Fassade eingeführt
  • Exception-Hierarchie: ParseException, SingularJacobianException, NaNException
Phase 3 — Strategy Pattern
Strategy Pattern und neue Solver

Der Solver wurde mit dem Strategy-Pattern umgeschrieben:

  • Interface SolverStrategy mit solve(SystemData, boolean)
  • Neue Solver: NewtonArmijoSolver, LevenbergMarquardtSolver, BroydenSolver, HomotopySolver
  • AbstractSolver liefert gemeinsame Infrastruktur (Iteration, Jacobi-Aufbau)
  • SolverConfig (Builder-Pattern) kapselt alle Parameter
  • SolverFactory mappt SolverType → SolverStrategy
Phase 4 — GSPAR
GSPAR Sparse-LU Solver Port

Der 3.259-zeilige Fortran GSPAR-Code (Grund, WIAS Berlin, ~1994) wurde nach Java portiert in vier neue Klassen: SparseMatrix, GSPARWorkspace, GSPAR, GSPARPseudoCode. Sechs Bugs aus dem originalen Fortran (vier von Borchardt dokumentiert, zwei unabhängig gefunden) wurden beim Portieren behoben. Zwei neue GSPAR-basierte Solver: GSPARSolver und NewtonArmijoGSPARSolver.

Phase 5 — Stabilisierung
Bug-Fixing und Stabilisierung

Über 20 Bugs wurden identifiziert und behoben. Die kritischsten: BF-01 (InitGuessApplier HashMap.replace), BF-02 (evaluateF-Timing), BF-03 (Jacobi Race Condition), BF-04 (Variable Scaling), BF-05 (GSPAR DLSOLA). Parallel: BroydenGSPARSolver, adaptive Reset/Checkpoint Strategie.

Phase 6 — INITIALIZE Fix
INITIALIZE-Block Fix · BatchRunner · InitialValueAnalyzer

Kritischer Bug: parseStructIfCondition() extrahierte Variablennamen mit line.split("[.]") — bei PARTM.F060.PT.SPEC ergab das 4 Teile statt 2, alle IF(VAR.SPEC==FIXED) Blöcke wurden übersprungen. Fix: lastIndexOf(".spec"). Nach dem Fix konvergierte NozzleSystem_4_fixed in 6 Iterationen.

  • Neu: InitialValueAnalyzer (-DI) für Startwertoptimierung
  • Neu: Batch-Modus via CSV-Input mit Warm-Start (BatchRunner)
  • Neu: PhysicalProjector respektiert User-Bounds über physikalische Defaults

NEU Phase 11 — v2.16 bis v2.12
Solver-Stabilisierung · Jacobi-Equilibrierung · Armijo-Refactor (R-01)
  • v2.16 — 7-Solver-Test-Stabilisierung: Alle sieben Solver-Typen (NEWTON_ARMIJO, LEVENBERG_MARQUARDT, HOMOTOPY, BROYDEN, NEWTON_SPARSE, NEWTON_SPARSE_ARMIJO, BROYDEN_SPARSE) auf NozzleSystem_4_fixed.cas verifiziert. JacobiEquilibrator-Klasse als Vorbereitung für R-01 implementiert (noch nicht in Solve-Loop integriert).
  • v2.12 — R-01 Jacobi-Equilibrierung umgesetzt: Neuer Skalierungsmodus EQUILIBRATE (Sinkhorn-Knopp R·J·C). Im selben Schritt wurde ein latenter Bug in den Inline-Armijo-Routinen der vier Newton-Armijo/Broyden-Solver behoben — Probe-Schritte wurden bei aktiver Skalierung im skalierten Raum auf physikalische Werte addiert, was Armijo de facto deaktiviert hatte. Inline-Armijo wurde in den armijoStep-Hook von AbstractSolver verlagert; Probe-Schritte laufen jetzt im Originalraum mit dxOrig. DIAGONAL und UNIT_INTERVAL funktionieren dadurch ab v2.12 erstmals korrekt. Bei NONE-Skalierung bit-exakt rückwärtskompatibel zu v2.16.
  • v2.12 — LM komplette Neufassung (v3b Newton-Direkt-Hybrid): Acht Iterationen lang versucht den LM-Solver auf NozzleSystem mit EQUILIBRATE konvergent zu kriegen. Erkenntnis nach Iter 5: die klassische LM-Normalengleichung (JᵀJ+μ·D)·dx = -Jᵀ·f quadriert die Konditionszahl. Bei n=303 mit kappa=4.6×10¹¹ wird das numerisch unbrauchbar. Lösung: bei kleinem μ (Levenberg-Form: μ < 10⁻⁴; Marquardt: μ < 10⁻⁶) direkte Newton-Inversion dx = -J⁻¹·f statt Normalengleichung — bit-identisch zu Newton-Armijo's Schritt. Resultat: NozzleSystem konvergiert mit -S:LEVENBERG_MARQUARDT -SC:EQUILIBRATE in 5 Iter, 0.36 s. Strukturell jetzt analog zu Newton-Armijo: computeStep macht NUR LGS, armijoStep macht Liniensuche mit weightedNormSq-Akzeptanz, μ-Adaption gekoppelt an Armijo-α.
  • v2.12 — Homotopy-Erweiterungen (zwei neue Solver, beide experimental):
    • ARC_LENGTH: Bogen-Längen-Continuation im erweiterten Zustand y=(x,t) mit sphärischer Bogen-Norm. Konzeptionell für Pfade mit Wendepunkten/Bifurkationen. Auf NozzleSystem nicht produktiv konvergent: Initial-Tangente ist bei kappa(J₀)=5×10¹¹ extrem in x-Richtung dominiert, Predictor schießt nicht in t-Richtung weiter. 712 Zeilen Implementierung, mathematisch sauber, ungenügend für reale Modelle.
    • ADAPTIVE_LAMBDA: Pragmatischer Wrapper über Newton-Armijo. Phase 1 versucht direkten Solver mit geerbter Skalierungsstrategie (auf NozzleSystem: 5 Iter Konvergenz). Phase 2 fällt auf λ-Continuation zurück mit F_λ = (1-λ)·J₀·(x-x₀) + λ·F(x). Phase 1 produktiv, Phase 2 divergiert auf NozzleSystem wegen Skalen-Mismatch im H_λ-System. 375 Zeilen, mit -SH:DIRECT=ON|OFF-Konfiguration.
  • v2.12 — Modell-Bound-Fix (NozzleSystem): GAMMA.Lower von 1.0 auf 1.05 angehoben. Verhindert 1/(γ-1)-Singularität wenn Newton's Schritt γ an die Bound treibt. Sofort-Effekt: alle Solver konvergieren auf NozzleSystem auch ohne Equilibrator. Erkenntnis: viele "Solver-Konvergenzprobleme" sind Modell-Probleme.

Stand am Ende von Phase 11 (v2.12):

  • 9 SolverTypes verfügbar: 7 produktiv (NEWTON_ARMIJO, NEWTON_SPARSE, NEWTON_SPARSE_ARMIJO, LEVENBERG_MARQUARDT, BROYDEN, BROYDEN_SPARSE, HOMOTOPY) + 2 experimental (ARC_LENGTH, ADAPTIVE_LAMBDA)
  • NozzleSystem mit GAMMA-Bound-Fix konvergiert in allen produktiven Solvern in 5-6 Iterationen (mit oder ohne EQUILIBRATE)
  • Doku komplett auf neuestem Stand inkl. zwei neuer Solver-Doku-Seiten (solver_arc_length.html, solver_adaptive_lambda.html)
  • 5 neue Lessons Learned (LL-21 bis LL-25) zu LM-Newton-Direkt-Hybrid, Architektur-Trennung, Continuation-Limits, Modell-Bounds

Bug Fix Log

IDs BF-01 bis BF-12 stammen aus der ursprünglichen Dokumentation (Phasen 1–6). B27, B28 und neuere wurden in v2.3–v2.5 behoben. IDs ohne Präfix sind interne Bezeichnungen.
🔴 Kritische Bugs (BF-01 bis BF-05)
BF-01
InitGuessApplier — Falscher Map-Key (Name statt Alias) FIXED
Die values-HashMap verwendet Variable-Aliases (z.B. \x_0) als Keys, nicht Variablennamen. InitGuessApplier rief values.replace(varName, value) auf — da varName nie ein Map-Key ist, tat replace() lautlos nichts. Alle INIT-Block-Werte wurden ignoriert.
Fix: values.replace(varAlias, value)
BF-02
evaluateF() nach statt vor applyStep() aufgerufen FIXED
Das Residuum fsum wurde aus dem alten f-Vektor (vor dem Schritt) berechnet, sodass der Konvergenzmonitor eingefroren wirkte.
Fix: evaluateF() wird jetzt nach jedem applyStep() aufgerufen.
BF-03
Jacobi-Parallelisierung Race Condition FIXED (deaktiviert)
MatrixSimple.setValueAt() ist nicht thread-safe. Parallele Jacobi-Konstruktion (Schwellwert n > 50) verursachte stille Datenverfälschung — non-deterministisch.
Fix: PARALLEL_JACOBI_THRESHOLD = 99999 (deaktiviert). Re-Aktivierung erfordert thread-safe MatrixSimple.
BF-04
Variable Scaling auf values-Map angewendet FIXED (deaktiviert)
VariableScaler.scaleValues() modifizierte dieselbe values-Map die evaluateF() liest. Thermodynamische Funktionen empfingen skalierte Werte (p≈1 Pa statt 100.000 Pa) → sofort NaN.
Fix: scaleValues()-Aufruf entfernt. Skalierung erfordert vollständige Architektur-Überarbeitung.
BF-05
GSPAR DLSOLA — Rückwärtssubstitution überschrieben FIXED
Originales Fortran DLSOLA hatte X(I)=B(I) nach Aufruf von DLSOLK, das Rückwärtssubstitutionsergebnis mit dem Vorwärtssubstitutionsergebnis überschreib.
Fix: Fehlerhafte Kopieranweisung entfernt.
🟡 Parser Bugs (BF-06 bis BF-09, B27–B28)
BF-06
Array-Variable: False Positive bei Unit-Annotation FIXED
EqnSysReader prüfte line.contains("[") auf der gesamten Zeile — Unit-Annotationen wie AS REAL(Unit:[m/s]) lösten fälschlich Array-Erkennung aus.
Fix: Nur den Teil vor " AS " prüfen.
BF-07
ATANGENS: Tippfehler im Token-Split-Pattern FIXED
setEquation() verwendete "ATANGES" (fehlendes N) im Regex-Split-Pattern. Gleichungen mit ATANGENS wurden falsch tokenisiert.
Fix: An allen 3 Vorkommen zu "ATANGENS" korrigiert.
BF-08
initTmpProcDef — NullPointerException FIXED
dataBlock.getTmpProcDef().setProcName(name) — getTmpProcDef() gab null zurück wenn vor dem ersten PROCEDURE-Block aufgerufen.
Fix: Neue Methode initTmpProcDef(String name).
BF-09
finaliseParsedData — Doppelter finally-Block (Kompilierfehler) FIXED
Nach Inlining der finaliseParsedData()-Logik blieb ein verwaister zweiter finally-Block außerhalb der umschließenden Methode — Kompilierfehler.
Fix: Entfernt.
B9
INITIALIZE StructConditional mit Punkt-Notation (kritisch) FIXED Phase 6
parseStructIfCondition() extrahierte Variablennamen mit line.split("[.]") und prüfte length == 2. Bei PARTM.F060.PT.SPEC==FIXED ergab der Split 4 Teile → alle 55 IF(VAR.SPEC==FIXED) Blöcke im INITIALIZE-Abschnitt wurden übersprungen. NozzleSystem_4_fixed konvergierte nicht.
Fix: lastIndexOf(".spec") extrahiert den vollen Variablennamen. Nach Fix: 6 Iterationen bis Konvergenz.
B10
initStructSwitches nur auf eqnData, nicht initData FIXED Phase 6
initStructSwitches() setzte Schalter nur für getAllEqnData(), nicht für getInitData() (separate Liste).
Fix: Beide Listen werden durchlaufen. Außerdem muss initStructSwitches vor InitGuessApplier aufgerufen werden.
B27
INITIALIZE: Bounds für Mehrfach-Punktnamen falsch extrahiert FIXED v2.3
PARTM.F060.PS.Upper = ... wurde falsch geparst — split(".") auf PARTM.F060.PS.Upper ergab parts[0] = "PARTM" statt "PARTM.F060.PS".
Fix: lastIndexOf('.') extrahiert alles vor dem letzten Punkt.
B28
INITIALIZE: Falsche Warnung bei normalem Mehrfach-Punktnamen FIXED v2.3
PARTM.F060.PS = 100000; im INITIALIZE-Block löste eine Warnung aus weil der Code jeden Namen mit Punkt als potentiellen .Lower/.Upper-Versuch interpretierte.
Fix: Warnung nur ausgeben wenn parts.length == 2 (genau ein Punkt im Namen).
🔵 Thermodynamische Bugs (BF-10 bis BF-12, B11)
BF-10
BIfunctions — Falscher Exponent im Düsen-Flächenverhältnis FIXED
Math.pow(fac, (-fac)) verwendete fac = 1 + (κ−1)/2·Ma² als Exponent statt des isentropen Exponenten fac1 = (κ+1)/(2(κ−1)).
Fix: Math.pow(fac, (-fac1))
BF-11
ISA-Drucktabelle: Ziffernvertauscher FIXED
ISA-Druck bei ~20 km Höhe war 5474.583 statt 5474.853 Pa (Ziffernvertauscher).
BF-12
ISA: Initialwert des Schichtindex FIXED
int index = 1 verursachte die Verwendung der falschen Atmosphärenschicht wenn die Höhe außerhalb des Tabellenbereichs lag.
Fix: index = -1 (kein Default).
B11
PhysicalProjector: lo=0 projiziert auf exakt 0 FIXED Phase 6
Bei User-Bound Lower=0 wurde auf 0 projiziert — für Variablen die im Nenner stehen (CF, FF, RE) ist das singulär.
Fix: Physikalisches Minimum als Fallback; nie exakt 0.
🟣 Refactoring-Bugs (v2.3–v2.5)
v2.3
EqnData: Javadoc innerhalb statt vor der Klasse FIXED v2.5
Klassen-Javadoc nach public class EqnData { eingefügt — Eclipse sah nested class. Symptom: "The nested type EqnData cannot hide an enclosing type" + 150+ Folgefehler.
Fix: Javadoc vor public class verschoben.
Prüfbefehl: grep -c "^public class EqnData" EqnData.java → muss 1 ergeben.
v2.3
EqnSysReader: Doppelter try-finally Block FIXED v2.5
Beim Refactoring von parseEquationSystemFile() blieb ein verwaister zweiter finally-Block außerhalb des neuen Scopes. Symptom: "stream cannot be resolved" + "Syntax error on token 'finally'".
Fix: Zweiten finally-Block entfernt.
Prüfbefehl: grep -c "finally" EqnSysReader.java → muss 1 ergeben.
v2.5
isCallEqn() beim FUNC_MAP-Einbau entfernt FIXED v2.5
Beim Einfügen der statischen FUNC_MAP stand die Einfügestelle exakt an der Position von isCallEqn() — die Methode wurde mitgelöscht. Symptom: "isCallEqn() is undefined" in 15 Klassen.
Fix: Methode wiederhergestellt.
