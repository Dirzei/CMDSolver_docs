Solver-Erweiterungen

R-01 Jacobi-Equilibrierung (Sinkhorn-Knopp) — Raum-konsistente Implementierung

Experimentell untersucht in v2.11-Entwicklung. Der JacobiEquilibrator (Sinkhorn-Knopp, 5 Iterationen) reduziert κ von 4.64e+11 auf 4.0 — theoretisch optimal. Aber die Implementierung scheitert an einem fundamentalen Architektur-Problem: dem Raum-Konflikt.

Die 4 Räume im aktuellen Solve-Loop

Originalraum x (Pa, K, kg/s)
  → buildJacobian()          J im gemischten Raum
  → equilibrator.apply()     J̃ = R·J·C,  f̃ = R·f (Kopie)
  → computeStep() / GSPAR    löst J̃·dx̃ = -f̃
  → equilibrator.unscale()   dx_orig = C·dx̃
  → armijoStep()             ← nutzt ORIGINALES f  ← KONFLIKT
  → applyStep()              x_neu = x + alpha·dx_orig
  → evaluateF()              f_neu im Originalraum

Armijo-Backtracking prüft ob ||F(x + alpha·dx)|| kleiner wird. Das lineare System wurde mit f̃ = R·f gelöst — der Schritt dx_orig = C·dx̃ ist korrekt für die skalierte Gleichung, aber wenn Armijo mit dem originalen f prüft, stimmen die Größenordnungen nicht überein. Armijo reduziert alpha auf 6e-05 oder der Schritt macht kaum Fortschritt.

Was für eine korrekte Implementierung nötig wäre

Ein einziger konsistenter skalierter Raum von Anfang bis Ende:

Skalierter Raum x̃ = D⁻¹·x
  F̃(x̃) = R · F(D · x̃)     ← skalierte Residuenfunktion
  J̃     = R · J · C         ← skalierte Jacobi
  Armijo mit F̃(x̃)          ← konsistent!
  dx_orig = C · dx̃          ← Rücktransformation am Ende

Das erfordert dass evaluateF() in den skalierten Raum transformiert wird — also dass BIfunctions (cpOfT, TsofAlt, MofCondiRatio) mit rücktransformierten physikalischen Werten aufgerufen werden. Das ist ein fundamentales Architektur-Redesign.

Bereits vorhandene Infrastruktur

JacobiEquilibrator.java ist vollständig implementiert mit compute(), applyToJacobian(), applyToRhs() und unscaleStep(). Die Klasse ist korrekt — das Problem liegt in der Integration in AbstractSolver.

Horizont:Vision >6 Monate Aufwand: Impact:Hoch
Wechselwirkung: Erfordert vollständiges Redesign von AbstractSolver (Armijo muss im skalierten Raum arbeiten), evaluateF() (Transformer-Pattern für BIfunctions), PhysicalProjector (muss Originalraum-Bounds kennen). Setzt voraus dass alle Subsysteme raum-bewusst werden — das ist der größte einzelne Eingriff in der gesamten Roadmap.
R-03 Homotopie: Echter Tangenten-Prädiktor + adaptive Schrittweite

Der aktuelle Homotopie-Prädiktor verwendet lineare Interpolation entlang des Pfades. Ein echter Tangenten-Prädiktor berechnet den Tangentialvektor dx/dt aus der erweiterten Jacobi [∂H/∂x | ∂H/∂t] via Nullraum-Berechnung. Das folgt dem Pfad genauer und ermöglicht größere Schritte.

Die adaptive Schrittweite (bereits teilweise im Code) sollte vollständig aktiviert werden: nach erfolgreichem Korrektor ds vergrößern, nach Misserfolg halbieren. Ein iterTarget von 3–5 Korrektoriterationen als Steuerung ist bereits in HomotopyConfig vorgesehen.

Nutzen: Verbesserte Konvergenz bei stark nichtlinearen Systemen (NozzleSystem mit κ~10²³). Das ist der wahrscheinlichste einzelne Fix um bisher nicht konvergierende Modelle zum Laufen zu bringen.

Horizont:Umgesetzt v2.10 · 03.05.2026 Aufwand: Impact:Hoch
Wechselwirkung: Nur HomotopySolver.java und HomotopyConfig.java. Kein Eingriff in andere Solver. Kann unabhängig von R-01 und R-02 entwickelt werden.
R-02 GMRES Linearer Solver

GMRES (Generalized Minimal Residual) löst das lineare System J·Δx = −F iterativ ohne die Jacobi explizit zu faktorisieren — nur Matrix-Vektor-Produkte J·v sind nötig. Das ist besonders wertvoll für: (1) sehr große Systeme n > 2000 wo selbst GSPAR-LU zu teuer wird, und (2) als innerer Solver im Broyden-Verfahren bei schlecht konditionierten Systemen.

Die Architektur ist vorbereitet: computeStep() in AbstractSolver ist der natürliche Einfügepunkt. GMRES würde als alternative Implementierung von computeStep() in einem neuen GMRESSolver eingesetzt.

Horizont:Langfristig 2–3 Monate Aufwand: Impact:Mittel
Wechselwirkung: Setzt R-01 (Skalierung) voraus da GMRES ohne Präkonditionierung bei schlecht skalierten Systemen divergiert. Synergiert mit R-18 (ILU-Präkonditionierung).
R-04 Trust-Region Solver (Dogleg)

Trust-Region Methoden schränken den Newton-Schritt auf eine Kugel mit Radius Δ ein und passen Δ adaptiv an. Das ist geometrisch intuitiverer als LM und hat bessere theoretische Konvergenzeigenschaften. Der Dogleg-Algorithmus kombiniert Newton-Schritt und Cauchy-Punkt (steiler Abstieg) und ist effizienter als reines Trust-Region.

Vorteil gegenüber LM: Besseres Verhalten bei Systemen die von near-singular zu well-conditioned wechseln — LM braucht viele Iterationen um μ anzupassen, Trust-Region passt Δ schneller an.

Implementierung: Neuer TrustRegionSolver extends AbstractSolver, neuer SolverType.TRUST_REGION, Eintrag in SolverFactory.

Horizont:Langfristig 1–2 Monate Aufwand: Impact:Mittel
Wechselwirkung: Nur solver/ Paket. Strategy-Pattern macht Hinzufügen neuer Solver isoliert — kein Eingriff in Parser oder BIfunctions. Kann parallel zu R-03 entwickelt werden.
R-05 Anderson Acceleration

Anderson Acceleration beschleunigt Fixpunkt-Iterationen durch Extrapolation aus m vergangenen Iterationspunkten. Besonders effektiv wenn Modelle natürlich als Fixpunkt-Iteration G(x) = x formuliert werden können — z.B. bei schwach gekoppelten Modulen mit Stream-Variablen.

Für die aktuelle Gleichungsystem-Formulierung ist Anderson weniger direkt anwendbar, aber für eine zukünftige modulare Stream-Architektur (R-15) wäre es die erste Wahl als schneller Iterationsverbesserer zwischen den Modulen.

Horizont:Vision >6 Monate Aufwand: Impact:Mittel (abhängig von R-15)
Wechselwirkung: Setzt R-15 (modulare Stream-Architektur) voraus. Vor R-15 hat Anderson wenig Mehrwert.
R-13 Relatives Abbruchkriterium

Aktuell bricht der Solver ab wenn fsum < tol_abs. Bei schlecht skalierten Systemen kann eine einzelne Pa-Gleichung (Residuum ~100) alle kg/s-Gleichungen (Residuum ~0.001) dominieren. Ein relatives Kriterium würde das ausgleichen:

converged = fsum < tol_abs
         || (fsum / fsum_initial) < tol_rel;  // z.B. 1e-4

Nutzen: Bessere Konvergenzdiagnose. Systeme die bei absolutem Kriterium divergieren können mit relativem Kriterium konvergieren.

Horizont:Umgesetzt v2.8 · 02.05.2026 Aufwand: Impact:Mittel
Wechselwirkung: Nur AbstractSolver.java, Zeile der Konvergenzprüfung. Neuer Parameter toleranceRelative in SolverConfig. Kein Eingriff in andere Klassen.

CAS-Dateierweiterungen

R-06 MIN(a,b) / MAX(a,b) als binäre Funktionen

MIN und MAX sind in vielen thermodynamischen Modellen nützlich — z.B. um Massenstrom-Limits, Druckgrenzen oder schaltende Regelcharakteristiken auszudrücken. CASprzak unterstützt Min/Max intern, aber EqnData übersetzt sie nicht aus der CAS-Syntax.

Implementierung: Zwei Einträge in FUNC_MAP sind allein nicht ausreichend da MIN/MAX binäre Funktionen mit zwei Argumenten sind — die Token-Trennung in FUNC_SPLIT_REGEX müsste angepasst werden. Alternativ: MIN/MAX als Hilfsvariablen via INITIALIZE formulieren.

Kurzfristige Alternative: Benutzer können MIN(a,b) durch 0.5*(a+b-ABS(a-b)) ausdrücken — das ist differenzierbar und benötigt keine Parser-Änderung.

Horizont:Umgesetzt v2.10 · 03.05.2026 Aufwand: Impact:Hoch
Wechselwirkung: EqnData.java (FUNC_MAP), EqnSysReader.java (Token-Trennung). Vorsicht: MIN/MAX sind nicht überall differenzierbar (Knick bei a=b) — Solver kann an diesen Stellen Probleme haben. Dokumentieren.
R-07 Zeilenkommentare in Gleichungszeilen (// inline)

Aktuell werden //-Kommentare nur am Zeilenanfang unterstützt. Kommentare hinter einer Gleichung — z.B. X = A * B; // Massenerhaltung — werden nicht korrekt abgetrennt. Der Parser liest das Semikolon als Gleichungsende, aber der Kommentar danach kann zu ParseWarnings führen.

Fix: In EqnSysReader.readLine() vor dem eigentlichen Parsing // als Zeilenende-Marker behandeln — alles dahinter abschneiden. Achtung: // könnte in String-Literalen vorkommen (Unit-Annotationen).

Horizont:Kurzfristig <1 Tag Aufwand: Impact:Mittel
Wechselwirkung: Nur EqnSysReader.java — readLine() Methode. Kein Eingriff in Parser-Logik oder Gleichungsverarbeitung.
R-08 SQR(x) = x² Expansion

SQR(x) ist in der CAS-Syntax vorhanden aber in FUNC_MAP als "nicht implementiert" markiert. CASprzak hat kein \sqr — aber SQR(x) kann trivial als (x)^2 expandiert werden, ähnlich wie TRUNCATE als floor implementiert ist.

Implementierung: Da SQR ein Argument hat aber einen binären Operator erzeugt, ist ein einfacher Eintrag in FUNC_MAP nicht ausreichend. Stattdessen: Regex-Ersetzung SQR\(([^)]+)\) → (\1)^2 vor der FUNC_MAP-Übersetzung.

Horizont:Kurzfristig <1 Tag Aufwand: Impact:Mittel
Wechselwirkung: EqnData.java — setEquation(). Vor der FUNC_MAP-Iteration einfügen. Kein Eingriff in andere Klassen.
R-09 INTEGERPARAMETER als echte Konstante

INTEGERPARAMETER wird aktuell geparst aber nur begrenzt ausgewertet. Für Modelle mit Array-Größen, FOR-Loop-Grenzen oder Schalter-Werten die als Integer definiert werden, wäre eine vollständige Unterstützung nützlich: INTEGERPARAMETER wird beim Parsing aufgelöst und überall wo der Name vorkommt durch den Wert ersetzt — ähnlich einem Präprozessor-Macro.

Nutzen: Modelle können parametrisch bezüglich Arraygröße oder Stufenzahl definiert werden ohne manuelle String-Substitution.

Horizont:Umgesetzt v2.10 · 03.05.2026 Aufwand: Impact:Mittel
Wechselwirkung: EqnSysReader.java (Parsing), EqnSysReaderDataBlock.java (Zustand), EqnData.setEquation() (Substitution vor Gleichungsverarbeitung).
R-10 SECTION…END für hierarchische Modellblöcke

Für sehr große Modelle (500+ Variablen) wäre eine hierarchische Block-Struktur wünschenswert — ähnlich wie Module in gPROMS oder Subsystems in ASPEN: 

SECTION MIXER
  W_IN AS REAL (...);
  W_OUT AS REAL (...);
  W_IN = W_OUT;  // Variablen werden automatisch zu MIXER.W_IN etc.
END SECTION

Alle Variablen innerhalb eines SECTION-Blocks werden automatisch mit dem Sektionsnamen präfixiert. Das macht die aktuelle Punkt-Notation (PARTM.F060.PS) explizit statt konventionell.

Horizont:Vision >6 Monate Aufwand: Impact:Mittel
Wechselwirkung: Vollständige Überarbeitung von EqnSysReader erforderlich. Setzt R-11 (QNAME Token-Typ) voraus. Große Wechselwirkung mit allen Parser-Klassen. Abwärtskompatibel wenn SECTION optional bleibt.

Parser-Verbesserungen

R-11 QNAME als eigener Token-Typ

Aktuell werden qualifizierte Namen (PARTM.F060.PS) als einfache Strings behandelt. Das hat zu mehreren Bugs geführt (B27, B28, B9) weil der Parser an verschiedenen Stellen unterschiedliche Split-Strategien verwendet um den Variablennamen zu extrahieren.

Ein eigener QNAME-Token-Typ mit expliziten Feldern (prefix[], localName, suffix) würde diese Bugs strukturell ausschließen. Der Parser würde QNAME einmal erkennen und konsistent handhaben. Das ist die langfristig korrekte Lösung für die Bugklasse "Punktnamen-Parsing".

Horizont:Vision >6 Monate Aufwand: Impact:Gering kurzfristig / Hoch langfristig
Wechselwirkung: Vollständige Überarbeitung von EqnSysReader, EqnData, Variable, SystemData. Sehr großer Eingriff — nur sinnvoll zusammen mit R-10 (SECTION-Syntax).

Performance

R-12 Jacobi-Parallelisierung (Thread-sicheres MatrixSimple)

Der Jacobi-Aufbau ist der teuerste Teil jeder Newton-Iteration — er berechnet ∂Fᵢ/∂xⱼ für alle (i,j)-Paare sequenziell. Die Parallelisierung ist bereits vorbereitet (PARALLEL_JACOBI_THRESHOLD = 99999 deaktiviert sie) aber MatrixSimple.setValueAt() ist nicht thread-sicher.

Fix-Optionen:
Option A: Per-Row lokale Arrays — jeder Thread füllt eine Zeile, am Ende zusammenführen. O(n²) Speicher.
Option B: ConcurrentHashMap<Integer, double[]> als Backing-Store — threadsicher by design.
Option C: Für GSPAR: SparseMatrix direkt thread-sicher machen via Row-Locks.

Nutzen: Bei n=500 Gleichungen und 8 Threads: 6–7× schnellerer Jacobi-Aufbau. Der Gesamtspeedup liegt bei 3–5× da andere Teile (LU-Faktorisierung) nicht parallelisierbar sind.

Horizont:Langfristig 3–6 Wochen Aufwand: Impact:Hoch
Wechselwirkung: MatrixSimple.java (oder neues MatrixConcurrent), AbstractSolver.buildJacobian(), DerivativeMatrix.java. Thread-Safety muss mit dem -TEST Modus ausgiebig getestet werden — non-deterministische Fehler sind schwer zu finden.
R-18 ILU-Präkonditionierung für GSPAR/GMRES

Incomplete LU (ILU) verwendet die GSPAR-LU-Struktur als Präkonditionierer für GMRES. Der Präkonditionierer P ≈ J macht das konditionierte System P⁻¹J·Δx besser konditioniert — GMRES konvergiert in deutlich weniger Iterationen.

Da GSPAR bereits eine LU-Faktorisierung mit kontrollierbarem Fill-In liefert, könnte die ILU(0)-Variante (kein zusätzlicher Fill-In) fast kostenfrei aus der bestehenden GSPAR-Faktorisierung extrahiert werden.

Horizont:Vision >6 Monate Aufwand: Impact:Gering (Spezialfall große Systeme)
Wechselwirkung: Setzt R-02 (GMRES) voraus. Eingriff in GSPAR.java und GSPARWorkspace.java.

Architektur

R-14 SolverState — Warm-Start für Parameterstudien

Aktuell startet jeder BatchRunner-Run mit denselben Startwerten aus der CAS-Datei. Bei Parameterstudien über ähnliche Betriebspunkte wäre ein Warm-Start ideal: der Lösungsvektor des vorherigen Punktes wird als Startvektor für den nächsten verwendet.

Implementierung: Ein SolverState-Objekt kapselt den letzten Lösungsvektor und wird an SolverAPI.solve() übergeben. InitGuessApplier verwendet dann diesen Vektor statt der CAS-Defaults. Der Broyden-Solver kann zusätzlich seine Jacobi-Approximation mitführen.

Nutzen: Bei typischen Parameterstudien (Flugzustand-Sweep) konvergiert Newton mit Warm-Start in 1–3 statt 5–15 Iterationen.

Horizont:Umgesetzt v2.10 · 03.05.2026 Aufwand: Impact:Hoch
Wechselwirkung: Neue Klasse SolverState, Erweiterung von SolverAPI und BatchRunner, Anpassung von InitGuessApplier. Kein Eingriff in Solver-Algorithmen.
R-15 Modulare Stream-Architektur (CONNECT-Syntax)

Für Gesamtsystem-Modelle aus mehreren Komponenten (Kompressor + Brennkammer + Turbine + Düse) wäre eine modulare Verbindungssyntax wertvoll:

MODULE Compressor USES compressor.cas
MODULE Combustor  USES combustor.cas
CONNECT Compressor.PT_OUT = Combustor.PT_IN;
CONNECT Compressor.TT_OUT = Combustor.TT_IN;

Ein SystemAssembler würde alle Module laden, die CONNECT-Gleichungen hinzufügen und ein gemeinsames SystemData-Objekt erzeugen das dann normal von einem Solver gelöst wird.

Vorteil: Module können wiederverwendet und unabhängig getestet werden. Die Block-trianguläre Dekomposition (Tarjan SCC) kann Reihenfolge für sequentielle Vorlösung bestimmen.

Horizont:Vision >6 Monate Aufwand: Impact:Hoch
Wechselwirkung: Neue Klasse SystemAssembler, neue CAS-Syntax (erfordert Parser-Erweiterung), Namensraum-Management in SystemData. Setzt R-10 (SECTION-Syntax) voraus. Größter einzelner Entwicklungsaufwand im Roadmap.

GUI-Vorbereitung

Strategie: Keine eigene GUI-Implementierung — sondern die Basis so vorbereiten dass eine GUI als dünner Layer über SolverAPI aufgebaut werden kann. SolverResult mit writeToWriter() und formatAsString() sind bereits in v2.5 implementiert. Die folgenden Punkte schließen die Lücke.
R-16 SolverLogger Handler für JTextArea

Der SolverLogger verwendet java.util.logging — das Handler-System erlaubt es, Log-Einträge in beliebige Ziele zu routen. Ein GUI-Handler leitet alle LOG.*-Ausgaben in eine JTextArea um:

Logger root = Logger.getLogger("apps.eqnParser");
root.addHandler(new Handler() {
    public void publish(LogRecord r) {
        SwingUtilities.invokeLater(() ->
            textArea.append(r.getMessage() + "\n"));
    }
    public void flush() {}
    public void close() {}
});

Das ersetzt das alte System.out-Umpipping vollständig — keine globalen Eingriffe, Thread-sicher via invokeLater, filterbar nach Severity.

Horizont:Mittelfristig Aufwand: Impact:Hoch (für GUI)
Wechselwirkung: Kein Eingriff in CMDSolver-Code. Der Handler wird in der GUI-Schicht registriert — CMDSolver selbst weiß nichts davon. Perfekte Trennung.
R-17 SolverResult Ergebnis-Tabelle für GUI

SolverResult.getAllValues() und getRawOutput() liefern bereits alle Daten für eine Ergebnistabelle. Die GUI braucht ein TableModel das auf diesen Daten basiert:

class SolverResultTableModel extends AbstractTableModel {
    // Spalten: Name | Wert | Lower | Upper | Unit | Status | Konvergenz
    // Daten aus result.getRawOutput()
    // Filter: nur freie / alle / nur Warnings
}

ParseErrors könnten als separate Liste oder als farbig markierte Zeilen in der Tabelle angezeigt werden (rot = ERROR, gelb = WARNING).

Horizont:Mittelfristig Aufwand: Impact:Hoch (für GUI)
Wechselwirkung: Basiert auf SolverResult (v2.5 fertig) und OutputVariable. Kein Eingriff in CMDSolver-Kern. Gehört in gui/ Paket.
