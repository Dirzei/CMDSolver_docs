Checkliste vor jedem Commit

  • -TEST durchführen — alle 7 Solver auf SimpleSystem.cas konvergieren
  • Kein System.out — nur LOG.info/warning/severe
  • Kein GUI-Import in Backend — kein import javax.swing in apps/eqnParser/
  • Javadoc bei neuen public Methoden — mindestens @return und @param
  • Neue Klasse in SolverFactory registriert — falls neuer Solver
  • FUNC_MAP aktualisiert — falls neue CAS-Funktion
  • Nie v2.3 und v2.4 Dateien mischen — immer konsistenter Stand
  • EqnData: nur eine public class Deklaration — Javadoc muss VOR der Klasse stehen
  • EqnSysReader: nur ein try-finally Block in parseEquationSystemFile
  • ZIP neu bauen + Commit + Push + Tag setzen

Architektur — Vollständige Paketstruktur

Für: Ich kenne CMDSolver noch nicht. Ich möchte den Code vollständig verstehen bevor ich Änderungen vornehme.

CMDSolver ist in drei logische Schichten aufgeteilt die klar voneinander getrennt sind. Abhängigkeiten zeigen immer von oben nach unten — die untere Schicht kennt die obere nicht.

Datenfluss — CAS-Datei bis Ergebnis

Der vollständige Datenfluss von der CAS-Datei bis zum Ergebnisobjekt:

// ── 1. Einstieg (CLI oder API) ──────────────────────────────
CASSolver.main()  oder  SolverAPI.solve()
    │
    ▼
// ── 2. Parser ───────────────────────────────────────────────
EqnSysReader.parseEquationSystemFile("model.cas")
    │  liest Zeile für Zeile via readLine()
    │  expandElseIf() — ELSEIF Pre-Processing
    │  EqnSysReaderDataBlock sammelt während des Parsens
    │
    ▼ gibt zurück
SystemData {
    allEqnData: List<EqnData>   // alle Gleichungen
    allVaris:   List<Variable>   // alle Variablen
    parseErrors: List<ParseError> // Fehler mit Zeilennummer
    iniVals[], lowVals[], uppVals[] // Startwerte + Bounds
}

// ── 3. Orchestrierung ───────────────────────────────────────
EqnSystem.run(sysData, useInit, solverCfg)
    │  initStructSwitches() — IF(VAR.SPEC) auswerten
    │  InitGuessApplier.apply() — INITIALIZE-Block anwenden
    │  SolverFactory.create(cfg) → konkreter Solver
    │
    ▼
AbstractSolver.solve(sysData, values, useInit)
    │  Hauptiteration:
    │  ┌─────────────────────────────────────────┐
    │  │  buildJacobian() → DerivativeMatrix      │
    │  │      EqnData.getDerivatives(values)      │
    │  │      CASprzak symbolisch → GeneralFunction│
    │  │  computeStep() → Δx  [solver-spezifisch] │
    │  │  x ← x + α·Δx                           │
    │  │  PhysicalProjector.project(x, sysData)   │
    │  │  fsum = Σ|EqnData.calcFunc(values)|      │
    │  │  if fsum < tol: CONVERGED                │
    │  └─────────────────────────────────────────┘
    │
    ▼ gibt zurück
List<OutputVariable>  →  SolverResult

// ── 4. Ergebnis ─────────────────────────────────────────────
SolverResult {
    converged, iterations, finalResidual
    getValue("PARTM.F060.PT")  // O(1) via HashMap
    writeToFile() / writeToWriter() / formatAsString()
    getParseErrors()
}

Bekannte Bugklassen — Geschichte und Fixes

Diese Bugs sind behoben. Die Dokumentation verhindert dass sie erneut eingebaut werden.

✅ BUG B27 — FIXED in v2.3
INITIALIZE-Block: Bounds für Mehrfach-Punktnamen
Problem: PARTM.F060.PS.Upper = ... wurde falsch geparst. Der Code verwendete parts[0] nach Split auf "." — bei PARTM.F060.PS.Upper war das PARTM statt PARTM.F060.PS.

Fix: lastIndexOf('.') statt Split: 
String lhs = checkParts[0].trim();
int lastDot = lhs.lastIndexOf('.');
this.initFuncVar = (lastDot > 0) ? lhs.substring(0, lastDot) : lhs;
Datei: EqnData.java, Methode setEquation()
✅ BUG B28 — FIXED in v2.3
INITIALIZE: Warnung bei normalem Mehrfach-Punktnamen
Problem: PARTM.F060.PS = 100000; im INITIALIZE-Block löste eine Warnung aus weil der Code dachte es wäre ein fehlerhafter .Lower/.Upper-Versuch.

Fix: Warnung nur ausgeben wenn parts.length == 2 (also genau ein Punkt im Namen): 
if (parts.length == 2) {
    LOG.warning("Unexpected INITIALIZE option '" + parts[1] + "'...");
}
Datei: EqnData.java, Methode setEquation()
✅ BUG — FIXED in v2.5
EqnData: doppelte Klassendeklaration durch falsch platzierten Javadoc
Problem: Beim Javadoc-Refactoring wurde der Klassen-Javadoc-Kommentar innerhalb der Klasse eingefügt statt davor — zwischen public class EqnData { und den Feldern. Eclipse sah eine nested class.

Symptom: "The nested type EqnData cannot hide an enclosing type"

Regel: Javadoc muss vor public class stehen. Prüfen: grep -c "^public class EqnData" EqnData.java muss 1 ergeben.

Datei: EqnData.java
✅ BUG — FIXED in v2.5
EqnSysReader: doppelter try-finally Block
Problem: Beim Refactoring von parseEquationSystemFile() entstand ein doppelter try-finally Block. Die Variable stream war im zweiten finally nicht mehr im Scope.

Symptom: "stream cannot be resolved" · "Syntax error on token 'finally'"

Regel: parseEquationSystemFile() darf nur einen try-finally Block haben — für das Schließen des BufferedReader. Prüfen: grep -c "finally" EqnSysReader.java muss 1 ergeben.

Datei: EqnSysReader.java
✅ BUG — FIXED in v2.5
isCallEqn() beim FUNC_MAP Refactoring weggefallen
Problem: Beim Einfügen der statischen FUNC_MAP in EqnData.java wurde die Methode isCallEqn() versehentlich gelöscht — sie stand genau an der Einfügestelle.

Symptom: "The method isCallEqn() is undefined for the type EqnData" in vielen Solver-Klassen.

Regel: Nach jedem größeren Refactoring in EqnData.java prüfen ob alle public Methoden noch vorhanden sind.

Fallstricke — Was man nicht tun darf

GUI-Imports in Backend-Klassen
Kein import javax.swing.* oder import gui.utils.* in apps/eqnParser/. Das verhindert Einbettung in Frameworks ohne Swing. Einzige Ausnahme: writeEqn4c() und writeDeriv() in EqnData die explizit als GUI-only markiert sind und langfristig ausgelagert werden sollen.
System.out statt Logger
Kein System.out.println() oder System.err.println() in Backend-Klassen. Immer LOG.info/warning/severe() verwenden. Für ein Framework ist unkontrollierter stdout-Output nicht akzeptabel.
Versionen mischen
Nie Dateien aus v2.3 und v2.4 im selben Eclipse-Projekt mischen. v2.4 EqnSysReader ruft ParseError auf die in v2.3 nicht existiert. Immer alle Dateien einer Version gleichzeitig einspielen.
FUNC_MAP Reihenfolge
Längere Funktionsnamen müssen vor kürzeren in FUNC_MAP stehen. ASINH vor SINH, ATANGENS vor TANGENS. Sonst wird z.B. ASINH zu asinhH weil SINH zuerst matcht.
Tag-Erstellung in Eclipse
Tags nie über Git Repositories → Tags → Create Tag erstellen — "Existing Targets" ist dort leer. Immer über Team → Show in History → Commit rechtsklicken → Create Tag.
HomotopySolver nicht über SolverFactory
SolverFactory.create() unterstützt HOMOTOPY nicht — der Homotopie-Solver braucht eine eigene HomotopyConfig. Immer direkt instantiieren oder über EqnSystem.runHomotopy().
