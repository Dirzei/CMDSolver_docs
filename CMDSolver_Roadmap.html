Kontext: CMDSolver v2.3 ist ein stabiler, funktionsfähiger Gleichungssystem-Solver der als eigenständiges Command-Line-Tool und als einbettbare Bibliothek konzipiert ist. Diese Analyse beschreibt konkrete Verbesserungsmöglichkeiten in sechs Bereichen — geordnet nach Thema, mit realistischer Aufwandsschätzung und Priorität. Keine GUI-Themen — Fokus liegt auf Code-Qualität, Robustheit und Dokumentation.

Logging & Fehlerbehandlung

Der größte technische Schulden-Posten in v2.3: 128 Stellen im Code verwenden noch System.out.println oder System.err.println statt dem bereits vorhandenen SolverLogger-Framework. Das ist besonders problematisch für die geplante Einbettung in ein anderes Framework — dort ist unkontrollierter stdout-Output nicht akzeptabel.

System.out.println("Variable not in HashList: " + var + " for Eqn: " + eqn);

Parser & EqnData

String-basiertes Parsing — Robustheit

Der aktuelle Parser in EqnData.java arbeitet mit einer langen Kette von toUpperCase().replaceAll()-Aufrufen. Das funktioniert für die bekannten Modelle, hat aber strukturelle Schwächen:

ProblemBeispielRisikoFix-Aufwand
Mehrfaches toUpperCase() pro Gleichung eq.toUpperCase().contains("SINH") — n-mal ausgeführt Performance bei großen Systemen Gering
Reihenfolge der replaceAll kritisch SIN vor ASIN würde ASIN → Asin erzeugen Stille Fehler bei falscher Reihenfolge Teilweise behoben in v2.3
Variablenname-Extraktion via split() split("=|\\*|SQRT|...") — fehleranfällig bei neuen Funktionen Neue Funktion vergessen → Variable nicht erkannt Mittel
QNAME kein eigener Token-Typ PARTM.F060.PS als String → B27/B28 Bugklasse Langfristig strukturelle Schwäche Hoch

Kurzfristige Verbesserung: replaceAll konsolidieren

Die Funktionsübersetzung in EqnData.java kann auf eine Map-basierte Übersetzungstabelle umgestellt werden — wartbarer und erweiterbar ohne Reihenfolge-Risiko:

// Statt langer if-Kette:
private static final Map<String, String> FUNC_MAP = new LinkedHashMap<>();
static {
    // Längere Matches zuerst — Map ist ordered
    FUNC_MAP.put("ATANGENS", "atan");
    FUNC_MAP.put("TANGENS",  "tan");
    FUNC_MAP.put("ATANH",    "atanh");
    FUNC_MAP.put("TANH",     "tanh");
    // ...
}

// Anwendung:
String eq = this.eqn4Sys.toUpperCase(); // einmal!
for (Map.Entry<String, String> e : FUNC_MAP.entrySet()) {
    if (eq.contains(e.getKey())) eq = eq.replace(e.getKey(), e.getValue());
}

Solver-Qualität

Skalierung — aktuell ungenutzt

Die ScalingStrategy-Infrastruktur ist in SolverConfig bereits vorhanden, aber der Default ist NONE. Bei Systemen mit sehr unterschiedlichen Größenordnungen (Druck in Pa ~1e5, Massenbrüche ~1e-3, Flächen ~1e-2 m²) verbessert Skalierung die Konditionszahl der Jacobi-Matrix erheblich.

StrategieBeschreibungStatus
NONE Keine Skalierung — bisheriges Verhalten ✅ Default
ROW_NORM Zeilennormierung der Jacobi — einfachste Verbesserung Infrastruktur vorhanden
VARIABLE_SCALE Skalierung über Variablen-Bounds (Lo/Hi bekannt) Infrastruktur vorhanden
Automatische Skalierung via Jacobi-Diagonale Van der Sluis / Curtis-Reid — optimal für gemischte Systeme Nicht implementiert

Konvergenzerkennung verbessern

Aktuell bricht der Solver ab wenn ||F|| < tolerance. Bei schlecht skalierten Gleichungen kann das täuschen — eine Gleichung mit großem Residuum in Pa dominiert über eine korrekte Gleichung in kg/s. Zwei Ergänzungen wären nützlich:

// Idee 1: Relatives Abbruchkriterium zusätzlich zu absolutem
boolean converged = fsum < tol_abs
                 || (fsum / fsum_initial) < tol_rel;

// Idee 2: Max-Residuum pro Gleichung loggen (bereits teilweise vorhanden)
// → welche Gleichung konvergiert nicht? → bessere Diagnose

Broyden — Rang-1-Update Stabilität

Der BroydenSolver akkumuliert Rang-1-Updates der inversen Jacobi. Bei langen Iterationsfolgen kann die approximierte Inverse degenerieren. Ein periodischer Reset (z.B. alle 25 Iterationen neu aufbauen) würde die Robustheit verbessern ohne den Vorteil des günstigen Updates zu verlieren.

MaßnahmeAufwandPriorität
ROW_NORM Skalierung als Standard aktivieren und testen Gering
Relatives Abbruchkriterium ergänzen Gering
Broyden periodischer Reset Gering
Van der Sluis Skalierung implementieren Mittel

Homotopie — komplexe Systeme

Das NozzleSystem_4-Modell (303 Gleichungen, κ~10²³) konvergiert mit dem aktuellen Homotopie-Solver nicht. Der relaxed-PhysicalProjector-Ansatz wurde versucht und zurückgenommen. Das Problem ist fundamentaler:

Diagnose

Kernproblem: Newton-Armijo als innerer Homotopie-Korrektor ist bei κ>10¹² ungeeignet. LM ist robuster aber konvergiert bei diesem Modell ebenfalls nicht zuverlässig. Die Ursache liegt wahrscheinlich in schlechten Startwerten für den Homotopie-Pfad bei t=0.

Mögliche Verbesserungen

MaßnahmeBeschreibungAufwandErfolgswahrscheinlichkeit
Adaptive Schrittweite ds wird nach Korrektorerfolg vergrößert / nach Misserfolg halbiert — weniger fixe Schritte Gering Mittel
Bessere Startwerte via -DI Vor Homotopie manuell physikalisch sinnvolle Startwerte aus einem einfacheren Modell einlesen Gering (Anwender) Hoch
Pseudo-Arc-Length mit Tangenten-Prädiktor Aktuelle Implementierung hat keinen echten Tangenten-Prädiktor — nur lineare Interpolation. Echter Tangenten-Vektor würde Kurvenverfolgung verbessern. Mittel Mittel-Hoch
Gleichungsnormierung vor Homotopie Gleichungen mit sehr unterschiedlichen Größenordnungen normieren bevor der Homotopie-Pfad gebaut wird — reduziert κ Mittel Mittel
Stagnations-Recovery Bei Stagnation automatisch zu LM wechseln, dann zurück zu Newton — bereits teilweise im Code Gering Mittel

Code-Robustheit & API

Fehlerbehandlung im Parser

Aktuell werden Parser-Fehler über ein isError()-Flag im DataBlock kommuniziert. Das gibt dem Aufrufer keine Information was falsch ist. Eine strukturierte Fehlerliste wäre für Einbettung und Debugging wertvoller:

// Idee: ParseError-Klasse statt Boolean
public class ParseError {
    private final int    lineNumber;
    private final String message;
    private final Severity severity; // ERROR, WARNING, INFO
}

// SystemData enthält dann:
List<ParseError> getParseErrors();
boolean hasErrors();   // nur ERROR-Severity
boolean hasWarnings(); // WARNING-Severity

CASSolver als einbettbare API

Für die geplante Einbettung in ein externes Framework braucht CASSolver eine saubere programmatische API — kein main() das argv parst, sondern direkte Methoden:

// Idee: SolverAPI-Fassade
SolverAPI api = new SolverAPI();
api.loadModel("model.cas");
api.setInitialValue("PARTM.F060.PT", 101325.0);
api.setSolverType(SolverType.NEWTON_SPARSE_ARMIJO);
SolverResult result = api.solve();

// Result enthält:
result.isConverged();
result.getVariableValue("FULLM.HTMAX");
result.getIterations();
result.getFinalResidual();

PhysicalProjector — Bounds-Quellen klarer trennen

Aktuell kommen Bounds aus zwei Quellen: CAS-Datei (.Lower/.Upper) und interne physikalische Limits (PhysicalProjector.detectPhysicalLimit()). Diese sind nicht immer klar dokumentiert. Eine explizite BoundSource-Annotation pro Variable würde Debugging erleichtern.
