CMDSolver

Modular Nonlinear Equation System Solver for Aerothermodynamic Systems
Java · Package: apps.eqnParser · 46 source files · GraalVM 25

1. Introduction

CMDSolver is a modular, command-line-driven solver for large nonlinear equation systems with a particular focus on aerothermodynamic process simulation. It follows the equation-oriented approach pioneered by simulators such as SpeedUp (later Aspen Technology): rather than solving component models sequentially, all equations are solved simultaneously as a single nonlinear system.

The solver accepts equation systems described in a structured text format (.cas files), builds symbolic Jacobian matrices via the CASprzak computer algebra library, and provides multiple Newton-type solution strategies suitable for systems ranging from a few dozen to many hundreds of equations.

Design Goals

  • Equation-oriented simulation of complex aerothermodynamic systems (gas turbines, jet engines, mixers, nozzles)
  • Robustness under poor initial conditions and near-singular Jacobians (κ ~ 1014)
  • Pluggable solver strategy pattern — solvers are interchangeable at runtime
  • Transparent logging and diagnostic output
  • Extensibility towards block-structured large sparse systems (n > 10,000)

2. Quick Start

Basic Solve

java CASSolver -I:engine.cas

With Variable Update File

java CASSolver -I:engine.cas -U:operating_point.txt

Select Solver

# Newton with Armijo line search (default)
java CASSolver -I:engine.cas -S:NEWTON_ARMIJO

# Levenberg-Marquardt (robust for ill-conditioned systems)
java CASSolver -I:engine.cas -S:LEVENBERG_MARQUARDT

# GSPAR sparse LU (recommended for n > 200)
java CASSolver -I:engine.cas -S:NEWTON_SPARSE

# Homotopy continuation for critical Ma=1 transitions
java CASSolver -I:nozzle.cas -S:HOMOTOPY -SH:CRITICAL

Output

Results are written to solver.log in the working directory and to stdout. Each iteration logs the current residual norm fsum and iteration counter ITER.

3.1 Parser Layer

The parser implements a line-by-line state machine in EqnSysReader. It reads .cas files and populates an EqnSysReaderDataBlock which is then finalised into a SystemData object.

After parsing, a post-processing step identifies which declared variables are actually referenced in equations and removes unused ones. This keeps the Jacobian as sparse as possible and is the foundation for future block-structured hierarchical variable names (dot-notation, e.g. turbine.stage1.T_in).

Symbolic derivatives are computed once via CASprzak's FunctionParser.parseInfix() and stored in a DerivativeMatrix. The Jacobian is then evaluated numerically each iteration by substituting current variable values.

3.2 Solver Architecture — Strategy Pattern

All solvers extend AbstractSolver which provides:

  • evaluateF() — evaluate all equations F(x) into vector f
  • buildJacobian() — assemble J from symbolic derivatives
  • applyStep() — apply dx to the values map
  • PhysicalProjector — bound-clamp after each step (T≥1K, p≥1Pa, Ma∈[0,10])
  • ResidualNormalizer — optional relative residual (‖F‖ / ‖F(x₀)‖)

Concrete solvers override only computeStep(J, f, values, …), which returns the Newton step vector dx.

3.3 GSPAR Sparse Solver Architecture

GSPAR (Grund, WIAS Berlin, ~1994) is a direct sparse LU solver ported from Fortran to Java. It operates in two phases:

PhaseWhenCostMethods
Structure analysisOnce (first iteration)O(nnz · fill-in)dllugc → dllugb → dlluga → dllugd → dldsp1
Numerical solveEvery Newton iterationO(nnz)dlfatr → dldint → dlsint

The key innovation is pseudo-code generation: after the structure is analysed, the elimination order is encoded as a compact integer program (pseudo-code). Subsequent re-factorisations simply interpret this program — no symbolic analysis is repeated.

3.4 Thermodynamic Built-in Functions

BIfunctions.java contains approximately 80 aerothermodynamic functions covering: JANAF polynomials for specific heat capacity cp(T), enthalpy h(T), entropy s(T,p); ISA standard atmosphere; isentropic nozzle flow; evaporation; and mixture properties for wet/dry air.

4. Newton-Armijo Solver

Type: -S:NEWTON_ARMIJO (default)

Classical Newton-Raphson with Armijo backtracking line search. Each iteration:

  1. Build full Jacobian J(xₖ) via symbolic derivatives
  2. Solve J·dx = −F(xₖ) via Gauss-Jordan elimination
  3. Armijo search: find α such that ‖F(xₖ + α·dx)‖² ≤ ‖F(xₖ)‖²·(1 − c₁·α)
  4. Update xₖ₊₁ = xₖ + α·dx

Convergence

Quadratic convergence near the solution. Requires a reasonably good starting point. Verified on the 623-equation aerothermodynamic benchmark system — converges in ~12 iterations, 2 more than the pre-refactoring version (acceptable overhead from line search).

5. Levenberg-Marquardt Solver

Type: -S:LEVENBERG_MARQUARDT

Adaptive damping strategy. Solves the modified system (JᵀJ + μI)·dx = −Jᵀ·F where μ is adapted via the gain ratio ρ = (‖F(x)‖² − ‖F(x+dx)‖²) / (model improvement). Recommended for systems near a sonic transition (Ma → 1) where the Jacobian becomes singular.

The adaptive μ schedule:

  • ρ > 0.75 → μ ← μ/3 (step accepted, reduce damping)
  • ρ < 0.25 → μ ← μ·4 (step rejected, increase damping)

6. Broyden Quasi-Newton Solver

Flag: -S:BROYDEN

Rank-1 Broyden update avoids full Jacobian rebuilds between resets. The update formula:

J_{k+1} = J_k + (y_k − J_k·s_k) · s_kᵀ / (s_kᵀ·s_k)
where  s_k = x_{k+1} − x_k,   y_k = F(x_{k+1}) − F(x_k)
✓ Verified: Adaptive Broyden converges on 623-equation benchmark With -S:BROYDEN -SB:RESET=10: 11 iterations vs 12 for Newton-Armijo, with only 2–3 Jacobian builds instead of 12 — significant saving in F-evaluations.

Adaptive Reset Strategy with Checkpoint/Rollback

The reset interval is managed adaptively — it starts at max(1, resetInterval/2) and adjusts based on convergence behaviour:

EventAction
Good step: fsum < lastFsum × 0.8Interval +1 (up to resetInterval)
Divergence: fsum > checkpoint × 2.0Rollback to checkpoint, interval ÷2
3 consecutive rollbacksNewton fallback mode
Good step in fallbackResume adaptive Broyden

7. Homotopy / Arc-Length Continuation

Type: -S:HOMOTOPY

Embeds the original system F(x) = 0 into a parameter family H(x,t) = (1−t)·F(x₀) + t·F(x) = 0 and traces the solution path from t=0 (trivially x=x₀) to t=1 (the desired solution). Uses arc-length parameterisation to navigate past turning points.

Each continuation step consists of a predictor (tangent) and corrector (inner Newton solve). The inner solver is configurable via -SH:INNER.

Bekannte Einschränkung — Systeme mit Schallübergängen

⚠ Lineare Homotopie versagt bei Schallübergangs-Bedingungen
Systeme die explizite Schallgrenz-Gleichungen enthalten (z.B. kritisches Druckverhältnis PTQPCRIT, Mach-Zahl-Übergänge Ma→1) können mit der linearen Homotopie nicht konvergieren — auch mit -SH:CRITICAL. Der Korrektor erreicht typischerweise fsum ~1e-2 bis 1e-1 und stagniert dann.

Physikalische Ursache

Die lineare Homotopie verwendet als Startpunkt die Linearisierung:

H(x, t) = (1-t)·J₀·(x-x₀) + t·F(x) = 0

Für kleine t dominiert der lineare Term J₀·(x-x₀). Eine Gleichung wie:

PTQPCRIT = PT / ((1 + (γ-1)/2·Ma²)^(γ/(γ-1)))

ist am Schallpunkt (Ma=1) hochgradig nichtlinear — der Gradient ∂F/∂Ma springt dort. Die lineare Näherung J₀·(x-x₀) kann diese Nichtlinearität nicht abbilden. Für bestimmte t-Werte zwischen 0 und 1 hat das Homotopie-System H(x,t)=0 physikalisch keine Lösung — der innere Korrektor-Solver stagniert an einem Schein-Fixpunkt mit endlichem Residuum.

Erkennungsmerkmale im Log

  • fsum fällt rasch auf ~1e-2 bis 1e-1 und ändert sich dann nicht mehr
  • Immer dieselbe Gleichung dominiert das Residuum (z.B. PTQPCRIT)
  • κ bleibt konstant auf CRITICAL-Niveau (~1e+15)
  • ||dx|| kollabiert auf <1e-7 während fsum stagniert
  • "LM: all retry attempts failed" am Ende

Empfehlung

Für Systeme mit Schallübergängen:

  • Primär: -S:NEWTON_ARMIJO -DI — wenn der INITIALIZE-Block physikalisch sinnvolle Startwerte setzt, konvergiert Newton direkt (NozzleSystem_4_fixed: 6 Iterationen)
  • Alternativ: Quadratische Homotopie (nicht implementiert) — verwendet F₀(x) = F(x₀) + J₀·(x-x₀) + ½·H₀·(x-x₀)² als Startpunkt und erfasst auch nichtlineare Terme
  • Nicht empfohlen: -SH:CRITICAL für Systeme mit echten Schallübergängen — kleinere Schritte helfen nicht wenn der Homotopie-Pfad selbst keine Lösung hat

8. GSPAR Sparse LU Solver

Type: -S:NEWTON_SPARSE

Newton's method using the GSPAR sparse LU factoriser (Prof. Friedrich Grund, WIAS Berlin, ~1994) as the linear solver. For aerothermodynamic systems with n=623 equations and ~10 non-zeros per row, the Jacobian density is only ~1.6%, making sparse methods approximately 50× faster than dense Gauss-Jordan.

Algorithm Pipeline

First iteration (one-time):
  analyzeStructure()  — extract sparsity pattern from Jacobian
  GSPAR.factorize()   — symbolic + numeric LU (DLLUGC → DLLUGB → DLLUGA → DLLUGD)
  GSPARPseudoCode.generate() — encode elimination order as pseudo-code

Subsequent iterations (fast):
  A.transferValues()           — load new Jacobian values into AF array
  GSPARPseudoCode.interpretLU() — LU via pseudo-code (no structure re-analysis)
  GSPARPseudoCode.interpretFwBw() — forward + backward substitution

10. CAS File Format

The .cas format is a structured text language parsed by EqnSysReader. A minimal example:

VARIABLE
  T_in AS REAL(Value:288.15; Unit:[K]; Lower:200; Upper:2000; Descr:Inlet total temperature)
  p_in AS REAL(Value:101325; Unit:[Pa]; Lower:1; Upper:1e7; Descr:Inlet total pressure)
  Ma   AS REAL(Value:0.5;   Unit:[-]; Lower:0;  Upper:10;  Descr:Mach number)
  T_st AS REAL(Value:270;   Unit:[K]; Status:Fixed)
END

EQUATION
  T_st = T_in / (1 + (GAMMA-1)/2 * Ma^2);
END

INIT
  T_in: Value=290; Lower=200; Upper=2000;
END

Block Keywords

KeywordPurpose
VARIABLE … ENDVariable declarations with metadata
EQUATION … ENDEquation block — implicit form F(x)=0
INIT … ENDInitial guess overrides (applied before solve)
PROCEDURE … ENDBuilt-in function call block
FOR … ENDLoop expansion (array variables)
IF … ELSE … ENDConditional equations

11. Development History

Phase 1 — Original Monolithic Solver

The original codebase consisted of a single EqnSystem.java with all parsing, Jacobian assembly, and Newton iteration inlined. The solver used a damped Newton method without line search. Key characteristics:

  • GUI-coupled: solver code imported Swing classes (HTMLDocument, JTextPane)
  • Fixed-point damping (factor 0.5–1.0) instead of adaptive line search
  • All variables tracked by name string — aliases not separated
  • No exception hierarchy — errors returned as flags
  • Broyden variant (NewtonBroydenGMRES) existed as a separate class with GMRES as linear solver

Phase 2 — Structural Refactoring

A systematic refactoring separated concerns into distinct classes:

  • InitGuessApplier extracted from EqnSystem.run()
  • EqnSysReaderGui separated from backend EqnSysReader
  • SolverLogger introduced as a centralised logging facade
  • SolverException hierarchy: ParseException, SystemDimensionException, SolverRuntimeException, SingularJacobianException, NaNException

Phase 3 — Strategy Pattern and New Solvers

The solver was rewritten using the Strategy pattern with a clean interface:

interface SolverStrategy {
    List<OutputVariable> solve(SystemData sysData, boolean useInitData);
}

New solvers implemented: NewtonArmijoSolver, LevenbergMarquardtSolver, BroydenSolver, HomotopySolver. AbstractSolver provides shared infrastructure. SolverConfig (builder pattern) encapsulates all parameters. SolverFactory maps SolverType → SolverStrategy.

Phase 4 — GSPAR Sparse Solver Port

The 3,259-line Fortran GSPAR code (Grund, WIAS Berlin, ~1994) was ported to Java across four new classes: SparseMatrix, GSPARWorkspace, GSPAR, GSPARPseudoCode. Six bugs from the original Fortran (four documented by Borchardt, two found independently) were corrected during porting.

Phase 5 — Bug Fixing and Stabilisation

Over 20 bugs were identified and fixed across the codebase. The most impactful ones are documented in the Bug Fix Log below.

Phase 6 — INITIALIZE-Block Fix, Batch-Mode, InitialValueAnalyzer

Critical bug discovered and fixed: parseStructIfCondition() in EqnSysReader used line.split("[.]") to extract the variable name from conditions like IF(PARTM.F060.PT.SPEC==FIXED). For dotted variable names this always produced more than 2 parts, so valueLeft remained empty and all conditional INITIALIZE blocks were silently skipped. Fix: lastIndexOf(".spec") correctly extracts the full variable name regardless of dot count. This bug prevented NozzleSystem_4_fixed from converging — after the fix: 6 iterations.

Additional fixes: initStructSwitches() now processes both getAllEqnData() and getInitData() (separate lists); must run before InitGuessApplier. New InitialValueAnalyzer (-DI flag) for residual diagnosis, bounds quality check, propagation-init, and sensitivity analysis. Batch-mode via CSV input with warm-start. PhysicalProjector now respects user bounds over physical defaults; lo=0 projects to physical minimum rather than exactly 0.

12. Bug Fix Log

Critical Bugs

BF-01: InitGuessApplier — Wrong Map Key (values.replace with Name vs Alias)

Critical The values HashMap uses variable aliases (e.g. \x_0) as keys, not variable names. InitGuessApplier called values.replace(varName, value) — since varName is never a map key, replace() silently does nothing. All INIT block values were ignored. Fixed to values.replace(varAlias, value).

BF-02: evaluateF() called after applyStep()

Critical The residual fsum was computed from the old f vector (before the step), so the convergence monitor appeared frozen. Fixed: evaluateF() is now called after every applyStep().

BF-03: Jacobi Parallelisation Race Condition

Critical MatrixSimple.setValueAt() is not thread-safe. Parallel Jacobian construction (threshold n>50) caused silent data corruption. Fixed: PARALLEL_JACOBI_THRESHOLD = 99999 (disabled).

BF-04: Variable Scaling Applied to values Map

Critical VariableScaler.scaleValues() modified the same values map that evaluateF() reads. Thermodynamic functions received scaled values (p≈1 Pa instead of 100,000 Pa), immediately producing NaN. Fixed: scaleValues() call removed; scaling is pending a complete architectural redesign.

BF-05: DLSOLA — Backward Substitution Result Overwritten

Critical Original Fortran DLSOLA had X(I)=B(I) after calling DLSOLK, which overwrote the backward-substitution result with the forward-substitution result. Fixed by removing the erroneous copy.

Parser Bugs

BF-06: Array Variable Detection False Positive

EqnSysReader checked line.contains("[") on the entire line, triggering for unit annotations like AS REAL(Unit:[m/s]). Fixed: check only the part before " AS " using split(" as ")[0].

BF-07: ATANGENS Typo in Token Split Pattern

setEquation() used "ATANGES" (missing N) in the regex split pattern. Equations containing ATANGENS were tokenised incorrectly. Fixed: corrected to "ATANGENS" at all 3 occurrences.

BF-08: initTmpProcDef — NullPointerException

dataBlock.getTmpProcDef().setProcName(name) — getTmpProcDef() returned null if called before the first PROCEDURE block. Fixed: new initTmpProcDef(String name) method that instantiates a fresh ProcDef before setting the name.

BF-09: finaliseParsedData — Duplicate Finally Block

After inlining finaliseParsedData() logic, a stray second finally block remained outside the enclosing method, causing a compile error. Removed.

Thermodynamic Function Bugs

BF-10: BIfunctions Zeile 656 — Wrong Exponent in Nozzle Area Ratio

Math.pow(fac, (-fac)) used fac = 1 + (κ−1)/2·Ma² as exponent instead of the isentropic exponent fac1 = (κ+1)/(2(κ−1)). Fixed to Math.pow(fac, (-fac1)).

BF-11: ISA Pressure Table Digit Transposition

ISA pressure at ~20 km altitude was 5474.583 instead of 5474.853 Pa. Fixed.

BF-12: ISA Layer Index Initial Value

int index = 1 caused the wrong atmosphere layer to be used when the altitude was outside the table range. Fixed to index = -1.

Fix B9 — INITIALIZE StructConditional mit Punkt-Notation (kritisch)

parseStructIfCondition() extrahierte den Variablennamen mit line.split("[.]") und prüfte length == 2. Bei Variablennamen wie PARTM.F060.PT ergab der Split 4 Teile → Bedingung false → valueLeft="" → alle 55 IF(VAR.SPEC==FIXED) Blöcke im INITIALIZE-Abschnitt wurden übersprungen ("StructConditional has no else branch — skipped"). Fix: lastIndexOf(".spec").

13. Open Issues

13.1 Broyden Quasi-Newton — Resolved ✓

Status: Resolved via Adaptive Checkpoint/Rollback. Broyden with -S:BROYDEN -SB:RESET=10 converges in 11 iterations on the 623-equation benchmark with only 2–3 Jacobian builds instead of 12.

The root cause — κ ≈ 1014 causing sign flip in gradF0 after rank-1 updates — is mitigated by the adaptive strategy: if divergence is detected (fsum > 2 × checkpoint fsum), the solver restores the pre-update state and halves the Broyden interval.

Remaining improvement: GMRES as inner linear solver would allow larger reset intervals without divergence risk. Currently Gauss-Jordan on the materialised Jk limits stability for very ill-conditioned systems.

13.2 Variable Scaling — Architecture Incomplete

Status: Disabled — Pending Redesign

Scaling flags -SC:DIAGONAL and -SC:UNIT_INTERVAL are parsed but produce a warning and fall back to -SC:NONE. The fundamental problem is that scaling must be applied consistently throughout the entire solve loop:

  1. Scale the values map before Jacobian evaluation
  2. Build Jacobian in scaled space (∂F/∂x̃ = ∂F/∂x · s⁻¹)
  3. Solve scaled system
  4. Unscale dx before applying step
  5. Unscale values map before thermodynamic function calls

Step 5 conflicts with evaluating thermodynamic functions (which require physical units). A transformer pattern wrapping evaluateF() is the correct solution.

13.3 GMRES Linear Solver — Not Yet Implemented

GMRES is required as the inner linear solver for stable Broyden updates and for ILU-preconditioned iterations on near-singular systems. The algorithm structure is designed to accept a pluggable linear solver — GMRES would slot in as an alternative to Gauss-Jordan and GSPAR in computeStep().

13.4 Block-Structured Hierarchical Variable Names

The parser currently supports flat variable names. The infrastructure for dot-notation hierarchy (e.g. turbine.stage1.T_in) is partially in place: unused variables are already removed from the system after parsing. The remaining work is:

  • LEX-based parser for nested SECTION … END blocks
  • Automatic variable prefixing within sections
  • Block-triangular decomposition (Tarjan SCC) for ordering

13.5 Jacobian Parallelisation — Disabled

The threshold PARALLEL_JACOBI_THRESHOLD = 99999 disables parallel Jacobian construction. To re-enable safely, MatrixSimple must be made thread-safe either via per-row local arrays or ConcurrentHashMap-based storage.

13.6 Parser Error Reporting

Parse errors do not report line numbers. The ParseException class is prepared for line-number metadata but the parser state machine does not yet pass it through. Line counting exists in readLine(lCount, …) but is not propagated to exceptions.

13.7 GSPAR — First Real-World Test Pending

-S:NEWTON_SPARSE compiles and passes structural verification but has not yet been tested on the 623-equation benchmark. The first test run will reveal whether the Java port of GSPAR produces correct LU factorisation results.

14. Lessons Learned

14.1 Scaling Cannot Be Added Incrementally

The single most expensive mistake was attempting to add variable scaling as an optional layer on top of an existing architecture. Scaling is a global concern: the values map, the Jacobian, the line search, and the thermodynamic function evaluations must all agree on whether they operate in physical or scaled space. Retrofitting scaling into a system designed without it required multiple iterations and ultimately the feature had to be disabled. Lesson: design scaling into the architecture from the start, or treat it as a complete system rewrite.

14.2 Broyden Without GMRES Is Not Viable for Ill-Conditioned Systems

The original NewtonBroydenGMRES worked because GMRES inherently handles near-singular matrices. Replacing it with Gauss-Jordan on the materialised Broyden Jacobian J_k fails because: (1) explicit inversion amplifies condition number errors, and (2) after rank-1 updates, J_k is no longer the true Jacobian — it is only an approximation, and inverting a poor approximation with an ill-conditioned algorithm compounds the error rapidly. Lesson: always match the linear solver to the conditioning of the problem, not to implementation convenience.

14.3 HashMap.replace() Fails Silently on Missing Keys

HashMap.replace(key, value) returns null and does nothing if the key does not exist — no exception, no warning. This caused the InitGuessApplier bug (BF-01) where all initial values were silently discarded. The system appeared to run correctly but used default variable values. Lesson: prefer put() over replace() unless the "key missing → do nothing" semantics is explicitly desired, and add an assertion or log warning when replace() returns null.

14.4 Thread Safety Must Be Verified Before Enabling Parallelism

Enabling parallel Jacobian construction without verifying thread-safety of MatrixSimple.setValueAt() caused silent data corruption (BF-03). The corruption was non-deterministic — sometimes the solver converged, sometimes diverged — making it extremely hard to diagnose. Lesson: never add parallelism to shared mutable state without explicit synchronisation analysis.

14.5 Fortran Port — Sentinel Values and Index Conventions

Fortran uses 1-based array indexing and often uses 0 as a sentinel ("end of chain"). Java uses 0-based indexing. Converting GSPAR required systematically shifting all array accesses by -1 and replacing sentinel 0 with -1. Missing even one conversion causes silent out-of-bounds access (Fortran arrays are unchecked). Lesson: define a conversion convention before starting a Fortran port and enforce it mechanically — a single global search-and-replace strategy is insufficient for complex linked-list structures.

14.6 Debug Logging Invaluable for Convergence Diagnosis

The pattern of adding LOG.info("DEBUG Iter %d: fsum=%.3e ||dx||=%.3e") immediately revealed two separate bugs: the frozen fsum (BF-02, evaluateF timing) and the Broyden sign flip. Without this, both would have been dismissed as "solver doesn't converge" without actionable diagnosis. Lesson: instrument convergence loops with detailed per-iteration logging from the beginning, not as an afterthought.

14.7 The Equation-Oriented Approach Scales — Sequential-Modular Does Not

The SpeedUp/Aspen approach of solving all equations simultaneously, pioneered partly by Prof. Pantelides, is the right architecture for complex coupled systems. Sequential-modular simulation (solve component by component) breaks down for systems with strong recycle streams and feedback loops. CMDSolver's equation-oriented design handles these naturally. Lesson: for tightly coupled aerothermodynamic systems, invest in the equation-oriented infrastructure upfront — it pays back immediately in generality and robustness.

14.8 Symbolic Differentiation via CAS Is Accurate but Inflexible

CASprzak provides exact symbolic derivatives, eliminating finite-difference errors entirely. However, the library cannot differentiate built-in procedure calls (cpOfT, htofTTref, etc.) — these require analytical derivative implementations in BIfunctions. Finite-difference fallback (adaptive h = max(10⁻⁴|x|, 10⁻⁶)) was implemented for the 19 locations where symbolic derivatives are unavailable. Lesson: CAS-based differentiation is excellent for algebraic equations; supplement with carefully implemented analytical derivatives for complex built-in functions.
