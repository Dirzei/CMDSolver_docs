Modulare Stream-Architektur

Mai 2026 · Gedankenspiel / Roadmap

Ausgangslage — aktuelles monolithisches Modell

Das aktuelle CMDSolver-Modell ist ein flaches Gleichungssystem: alle Variablen (PARTM.F060.PT, FULLM.F166.W, …) und alle Gleichungen liegen in einem einzigen SystemData-Objekt. Der Solver sieht eine Jacobi-Matrix über alle 303+ Variablen gleichzeitig.

Vorteil heute: Vollständige Kopplung — der Solver kann globale Wechselwirkungen direkt erkennen. Druckgleichgewicht zwischen Core und Bypass wird automatisch als Teil desselben Gleichungssystems gelöst.

Nachteil heute: Ein Modell = eine Datei. Mixer, Jetpipe, Düse sind nicht austauschbar ohne die CAS-Datei manuell zu editieren.

Zielarchitektur — Module + Streams

In einer modularen Architektur ist jedes Bauteil (Mixer, Nozzle, Jetpipe) ein eigenständiges Modul mit definierten Ein- und Ausgängen. Streams verbinden Module und übertragen thermodynamische Größen wie Druck, Temperatur, Massenstrom.

Was ein Stream ist: Ein Stream ist ein benanntes Bündel thermodynamischer Zustandsgrößen an einem Querschnitt — analog zu den bestehenden PARTM.F060.* / PARTM.F066.* Blöcken, aber als formales Interface-Konzept mit Typ-Prüfung.

Was müsste geändert werden

① Stream-Typ definieren (neue Klasse)

Ein Stream ist eine typisierte Sammlung von Variablen an einer Modulgrenze. Das könnte direkt in der CAS-Syntax ausgedrückt werden:

// stream_types.cas — Stream-Typ-Definitionen
STREAMTYPE GasStream
  REAL PT;      // Totaldruck [Pa]
  REAL TT;      // Totaltemperatur [K]
  REAL W;       // Massenstrom [kg/s]
  REAL RGAS;    // Gaskonstante [J/kgK]
  REAL FAR;     // Fuel-air ratio [-]
  REAL WGR;     // Water-gas ratio [-]
END

② Modul-Syntax erweitern

Module deklarieren ihre Ein- und Ausgänge explizit. Der Parser muss MODULE, INLET, OUTLET als neue Schlüsselwörter kennen:

MODULE Mixer
  INLET:  CoreIn  AS GasStream;
  INLET:  BypassIn AS GasStream;
  OUTLET: MixOut  AS GasStream;

  // Interne Gleichungen — Variablen wie bisher
  GEOM.RMIXER AS REAL (...);
  ...

  // Gleichungen referenzieren Inlet/Outlet-Größen direkt
  MixOut.W = CoreIn.W + BypassIn.W;
  MixOut.TT = (CoreIn.W*CoreIn.TT + BypassIn.W*BypassIn.TT) / MixOut.W;
END

③ Topologie-Datei

Eine übergeordnete Datei verbindet Module über Streams:

SYSTEM NozzleSystem

  MODULE  mixer   USES "mixer.cas";
  MODULE  jetpipe USES "jetpipe.cas";
  MODULE  nozzle  USES "nozzle.cas";

  CONNECT mixer.MixOut   → jetpipe.Inlet;
  CONNECT jetpipe.Outlet → nozzle.Inlet;

END

④ Solver-Strategie: Gekoppelt oder sequenziell?

StrategieWieVorteilNachteilAufwand
Vollständig gekoppelt Module werden zu einem einzigen SystemData zusammengeführt — wie heute, nur strukturiert geladen Exakt dasselbe Konvergenzverhalten wie heute. Kein neuer Solver nötig. Verliert die Modularität beim Lösen. Große Jacobi. Gering
Sequenziell (Stream-iteration) Module werden nacheinander gelöst. Stream-Werte werden iteriert bis Konvergenz. Jedes Modul klein und gut konditioniert. Leicht parallelisierbar. Konvergenz nicht garantiert bei starker Rückkopplung. Braucht äußere Iteration. Mittel
Block-Newton Jacobi wird block-strukturiert — ein Block pro Modul. Stream-Variablen sind Kopplungsblöcke. Beste Konvergenz + Modularität. Strukturell wie GSPAR aber block-weise. Komplexe Jacobi-Assemblierung. Hoch
Empfehlung: Die einfachste und risikoärmste Strategie ist vollständig gekoppelt mit Merge — Module werden beim Laden zu einem einzigen SystemData zusammengeführt. Der Solver sieht nichts anderes als heute. Die Modularität wirkt nur auf Datei- und Modellierungsebene, nicht auf Solver-Ebene. Das ist in 2-3 Wochen umsetzbar ohne den Solver anzufassen.

Was CONNECT intern erzeugt

Eine CONNECT-Anweisung generiert automatisch Kopplungsgleichungen. Das sind einfache Gleichheitsbedingungen — nichts strukturell Neues:

// Topologie:
CONNECT mixer.MixOut → jetpipe.Inlet;

// Erzeugt automatisch folgende Gleichungen im merged SystemData:
jetpipe.Inlet.PT  = mixer.MixOut.PT;
jetpipe.Inlet.TT  = mixer.MixOut.TT;
jetpipe.Inlet.W   = mixer.MixOut.W;
jetpipe.Inlet.RGAS = mixer.MixOut.RGAS;
jetpipe.Inlet.FAR = mixer.MixOut.FAR;
jetpipe.Inlet.WGR = mixer.MixOut.WGR;

Diese Gleichungen sind lineare Identitäten — ihre Jacobi-Einträge sind ±1 und fügen keine numerische Schwierigkeit hinzu. Das ist strukturell identisch zu den bestehenden Kopplungen wie PARTM.F066.W = PARTM.F070.W die heute schon im monolithischen Modell existieren.

Einzige numerische Überlegung: Wenn Module stark rückgekoppelt sind (z.B. Nozzle-Gegendruck beeinflusst Mixer-Eintrittsbedingungen), ist die vollständig gekoppelte Strategie zwingend — sequenziell würde hier nicht konvergieren. Bei Triebwerkskomponenten in Reihe (Mixer → Jetpipe → Nozzle) ohne Rückkopplung wäre sequenziell möglich, aber der Merge-Ansatz ist trotzdem robuster.

Übergangsweg — bestehende CAS-Dateien bleiben kompatibel

Der entscheidende Vorteil des Merge-Ansatzes: bestehende monolithische .cas-Dateien funktionieren weiterhin unverändert. Die neue Topologie-Syntax ist optional — CASSolver erkennt am Datei-Suffix .sys dass ein modulares System vorliegt.

Phase 1 StreamDef + ModuleDef Klassen, STREAMTYPE/MODULE/CONNECT Parser-Erweiterung in EqnSysReader ~1 Woche
Phase 2 SystemAssembler: lädt Module, löst Namenskonflikte via Präfix, generiert CONNECT-Gleichungen, merged zu SystemData ~1 Woche

Optional Stream-Typ-Validierung (Einheitenkonsistenz), sequenzielle Solver-Strategie ~2 Wochen
Fazit: Die Solver-Implementierungen — Newton, LM, Broyden, GSPAR, Homotopie — müssen nicht angefasst werden. Die gesamte Arbeit liegt im Parser und im neuen Assembler. Der Aufwand ist überschaubar und das Risiko gering, weil der Kernalgorithmus unverändert bleibt.
