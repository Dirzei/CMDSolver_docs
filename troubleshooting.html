Konvergenzprobleme

❌ Solver meldet NOT_CONVERGED — keine Fehlermeldung
→ 1
Schlechter Startvektor? Diagnose-Modus aktivieren: -DI lässt InitialValueAnalyzer die Startwerte optimieren. Oft reicht das. 
java cmd.CASSolver -I:model.cas -DI
→ 2
Startvektor inspizieren: -DV:start.txt schreibt den tatsächlichen Startvektor vor Iteration 0. Physikalisch plausibel? Temperatur > 0K? Druck > 0Pa? 
java cmd.CASSolver -I:model.cas -S:NEWTON_ARMIJO -DV:start.txt
→ 3
Andere Solver versuchen: -TEST zeigt alle 7 Solver. Konvergiert einer davon → Startwert-Problem. Konvergiert keiner → Modell-Problem.
→ 4
Levenberg-Marquardt als robustere Alternative: Bei κ-Warnungen im Log immer LM versuchen. 
java cmd.CASSolver -I:model.cas -S:LEVENBERG_MARQUARDT -DI
→ 5
Homotopie als letztes Mittel: 
java cmd.CASSolver -I:model.cas -S:HOMOTOPY -SH:CRITICAL -SH:INNER=LEVENBERG_MARQUARDT
🔄 Solver iteriert bis maxIter ohne Verbesserung (fsum stagniert)
→ 1
fsum-Verlauf im Log prüfen: Sinkt fsum gar nicht? → Schlechter Startvektor oder falsches Vorzeichen in Gleichung. Sinkt fsum anfangs, stagniert dann? → Möglicherweise zwei Lösungen oder nahezu singuläre Jacobi.
→ 2
Residuen-Normierung aktivieren: Bei gemischten Einheiten (Pa + kg/s) kann eine Gleichung dominieren. -SN normiert auf Startwert-Residuen. 
java cmd.CASSolver -I:model.cas -SN
→ 3
Gleichgewicht prüfen: n freie Variablen = n Gleichungen? Log zeigt beim Start: Starting ... [n=X, maxIter=100, ...] — X muss der Anzahl freier Variablen entsprechen.

Parser-Fehler

⚠️ ParseError: "Variable not found" oder stille Fehler
→ 1
ParseErrors im SolverResult prüfen: 
SolverResult r = api.solve();
r.getParseErrors().forEach(e -> System.err.println(e.format()));
Jeder ParseError enthält Zeilennummer und Kontext.
→ 2
Variablenname-Tippfehler: CMDSolver ist case-insensitiv — aber Punkt-Notation muss exakt stimmen. PARTM.F060.PS ≠ PARTM.F060.Ps (Letzteres würde nach toUpperCase zu ersterem).
→ 3
Variable deklariert aber nicht in Gleichung: Freie Variable ohne Gleichung → System ist unterbestimmt. Jede freie Variable braucht genau eine Gleichung die sie "bestimmt".
⚠️ INITIALIZE-Block Override wird ignoriert
→ 1
Syntax für Mehrfach-Punktnamen: Für PARTM.F060.PS.Upper = ... muss der vollständige Name vor dem letzten Punkt stehen. Der Parser verwendet lastIndexOf('.'). 
INITIALIZE
  PARTM.F060.PS = 100000;          // Startwert
  PARTM.F060.PS.Upper = 200000;   // Upper-Bound
  PARTM.F060.PS.Lower = 50000;    // Lower-Bound
ENDINIT
→ 2
initStructSwitches vor INITIALIZE: Strukturelle IF-Bedingungen (VAR.SPEC==FIXED) müssen vor dem INITIALIZE-Block ausgewertet werden. Das macht EqnSystem automatisch — wenn der Aufruf fehlt (z.B. bei direktem EqnData-Aufruf) funktioniert INITIALIZE nicht.
🔴 Kompilierfehler: hunderte Fehler nach Datei-Update
→ 1
Versionsmischung: Wahrscheinlichste Ursache. Dateien aus v2.3 und v2.4+ dürfen nicht gemischt werden. v2.4's EqnSysReader ruft ParseError-Methoden auf die in v2.3's SystemData fehlen. Lösung: Alle Dateien aus demselben ZIP kopieren.
→ 2
Doppelte Klassendeklaration: 
grep -c "^public class EqnData" EqnData.java  // muss 1 ergeben
Wenn 2: Javadoc steht nach statt vor public class.

Konditionszahl-Warnungen

⚠️ Log: "kappa=4.62e+11 [POOR] — ill-conditioned Jacobian"

Konditionszahl κ misst wie empfindlich das System auf kleine Änderungen reagiert. κ > 10⁸ ist problematisch, κ > 10¹² gefährlich für Newton.

→ 1
Ursachen für hohes κ: Gemischte Einheiten (Pa ~ 10⁵, kg/s ~ 1, dimensionslos ~ 10⁻³) erzeugen riesige Spanne in der Jacobi. Verschiedene Größenordnungen werden direkt im Jacobi-Eintrag sichtbar.
→ 2
Sofortmaßnahme: Levenberg-Marquardt: LM ist robust bis κ ~ 10²⁵. Einfach Solver wechseln: 
java cmd.CASSolver -I:model.cas -S:LEVENBERG_MARQUARDT
→ 3
Mittelfristig: Gleichungen normieren: Gleichungen in Pa durch 1e5 teilen, kg/s-Gleichungen durch 1 lassen. Das reduziert die Spanne in der Jacobi und verbessert κ um 2–4 Größenordnungen.

NaN und Divergenz

💥 Log: "NaN detected — treating as divergence"
→ 1
Physikalisch unmöglicher Zwischenwert: Eine Gleichung hat einen Wert außerhalb des physikalischen Bereichs erzeugt — z.B. negative Temperatur in SQRT(T), Division durch Null. PhysicalProjector fängt viele Fälle, aber nicht alle.
→ 2
Bounds strenger setzen: Lower-Bounds für T (≥ 1K), p (≥ 1Pa), Flächen (≥ 1e-6 m²) verhindern physikalisch unmögliche Zwischenwerte. PhysicalProjector projiziert nur auf User-Bounds wenn diese enger sind als die physikalischen Defaults.
→ 3
Armijo-Liniensuche hilft: NEWTON_SPARSE_ARMIJO halbiert den Schritt wenn der Versuchspunkt NaN erzeugt. Ohne Armijo (NEWTON_SPARSE) kann NaN sofort auftreten.
📊 Homotopie meldet fsum = NaN

Das ist normal. Der Homotopie-Solver gibt kein fsum über den Standard-Kanal aus — er hat eine eigene interne Konvergenzprüfung über den Pfadfortschritt t → 1. Nur der isConverged()-Status ist maßgeblich.

Performance-Probleme

🐢 Solver ist sehr langsam bei großem System (n > 200)
→ 1
Sparse-LU verwenden: NEWTON_ARMIJO verwendet dichte LU (O(n³)). NEWTON_SPARSE_ARMIJO verwendet GSPAR Sparse-LU (O(nnz)) — bis 10× schneller.
→ 2
Broyden-Sparse für Parameterstudien: Wenn viele ähnliche Betriebspunkte gelöst werden: BROYDEN_SPARSE spart Jacobi-Neuaufbauten. ~9ms vs ~30ms für SimpleSystem.
→ 3
BatchRunner für Parameterstudien: CSV-Datei mit allen Betriebspunkten → -I:studie.csv. Läuft alle Punkte sequenziell mit Warm-Start-Option.

Häufige Fragen (FAQ)

Wie viele Gleichungen kann CMDSolver lösen?
Theoretisch unbegrenzt. Praktisch getestet bis ~600 Gleichungen (623-Gleichungen Benchmark). Mit GSPAR Sparse-LU sind 1000–2000 Gleichungen realistisch. Bei n > 2000 wird GMRES als linearer Solver benötigt (Roadmap R-02).
Warum ist die Jacobi dicht obwohl das System sparse aussieht?
In thermodynamischen Modellen hängen viele Variablen über physikalische Zusammenhänge zusammen — Gaszusammensetzung beeinflusst cp beeinflusst κ beeinflusst Schallgeschwindigkeit beeinflusst Machzahl usw. Das erzeugt trotzdem eine relativ dünn besetzte Jacobi (5–15% Besetzung) — GSPAR Sparse-LU ist dennoch deutlich schneller als dichte LU.
Kann ich CMDSolver in einem Multi-Thread-Kontext verwenden?
Ja — eine SolverAPI-Instanz pro Thread. Instanzen sind nicht thread-sicher untereinander, aber mehrere unabhängige Instanzen können parallel laufen. Der interne Jacobi-Aufbau ist aktuell nicht parallelisiert (PARALLEL_JACOBI_THRESHOLD = 99999).
Warum hat die CAS-Datei Semikolon am Ende jeder Gleichung?
Das Semikolon ist das Gleichungsende-Zeichen — der Parser behandelt es als Abschluss der Residuumsform LHS − (RHS) = 0. Ohne Semikolon kann der Parser nicht unterscheiden ob die Zeile weitergeht. In der AS-REAL-Kurzform ist das Semikolon ebenfalls obligatorisch.
Was bedeutet "Fixed" vs "Free" für eine Variable?
Fixed: Die Variable ist eine bekannte Randbedingung — ihr Wert ist vorgegeben und wird vom Solver nicht verändert. Free: Die Variable ist eine Unbekannte die der Solver bestimmt. Anzahl Free-Variablen muss gleich Anzahl der Gleichungen sein.
Kann ich die Lösung eines Betriebspunkts als Startvektor für den nächsten verwenden?
Mit der -DV: Option wird der aktuelle Startvektor in eine Datei geschrieben die dann mit -U: als Startvektor für den nächsten Lauf verwendet werden kann. SolverState Warm-Start (Roadmap R-14) wird das automatisieren.
Warum funktionieren ABS(), ROUND() und TRUNCATE() manchmal schlecht mit Newton?
Diese Funktionen sind an Knicken und Sprüngen nicht differenzierbar. Newton braucht glatte Ableitungen. An den Unstetigkeitsstellen (ABS bei 0, ROUND bei .5) ist die symbolische Ableitung undefiniert und die numerische Ableitung ungenau. Als Alternative: glatte Approximationen verwenden, z.B. ABS(x) ≈ SQRT(x^2 + ε) mit kleinem ε > 0.
Wie debugge ich eine Gleichung die immer NaN liefert?
Startvektor mit -DV:start.txt speichern, Werte manuell in einer Tabellenkalkulation nachrechnen. Welche Variable hat einen unmöglichen Wert? Dann Bounds für diese Variable strenger setzen und -DI aktivieren.
